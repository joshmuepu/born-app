## Architecture decisions (deviations from the design are marked ⚑)
- ⚑ Tape data lives in its **own database `tape.db`** (new tables only; `PRAGMA user_version` migrations like `media.db`) instead of extra tables in `media.db`: the media library is picture-centric (width/height/thumbnails, the Media UI lists every row), so audio there would leak into the pictures UI. Same safety property (older BORN never sees it; `.born` unchanged); deleting a recording never touches sermon data (separate DB).
- Files: managed copy in `<userData>/tapes/<sha256>.<ext>` (copy by default), or linked in place.
- Audio engine: a hidden renderer page `audio.html` (own `BrowserWindow`, `show:false`, `backgroundThrottling:false`) is the clock owner; files served by the existing `born-media://` protocol (new `tape` host, Range-capable). Main keeps the tape record (reducers in `shared/tapePlayback.ts`).
- The numbered paragraph is derived from `quoteToItem(row).slides[].marker` (the same split the reader and projector use), so a sync map always agrees with what the operator sees.
- Following: main turns tape position into a normal slide payload (`slide.tape` carries view data) and sends it through `showChannelSlide`, so history, other channels, Graphics and stage keep working.

### S8 measurements on the real tape (numbers only; whisper.cpp base.en)
- Whole tape (2 h 24 m 47 s = 8,688 s) with Apple-silicon GPU: **67 s CLI / 71 s through the app** (~122× real time). Aligner (word diff + anchors): **22 ms**.
- **Plausibility** (independent window check: of each paragraph's first 8 words, how many are heard between −1 s and +8 s of the proposed start): 363 paragraphs; mean **82 %**, median **88 %**, 10th percentile **63 %**; **90 %** of paragraphs have ≥ 60 % of their opening words heard in the window. Confidence separates the sure from the unsure: the 348 paragraphs at confidence ≥ 0.7 average 84 %; the 15 below average 44 % (those are what "Next least sure" walks first).
- **CPU only** (no GPU; 300 s clip from the middle; M4 Max): 4 threads **5.9 s** (51×), 2 threads **8.8 s** (34×), 1 thread **15.3 s** (19.7×).
- **Honest estimate for a modest Windows PC** (4 cores, no GPU; *not measured — to be run on the church PC*): a single modern x86 core without Apple's accelerators is roughly 3–4× slower than one M4 core, so about 5–7× real time per thread and perhaps 12–25× with four threads. That puts the 2 h 25 m tape at **about 6–30 minutes** (call it "10–30 min, run it before the service, not during"); the large models are ~10× slower and not recommended there. Memory for base.en is under 500 MB.
- Not measured: other languages (English model only), noisy room recordings, music-heavy tapes. The result is always a proposal reviewed in the editor.
